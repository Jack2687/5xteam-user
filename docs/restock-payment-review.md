# 付款风控与补货队列

原账号和订单保留待核实，不自动重试原付款，不记为死号。供应商订单同时具备远端订单 ID、明确 failed、结算 settled，且未明确禁止重试时，失败任务不再占用补货在途，持久化一次新账号替补机会。

每笔失败只关联一个新账号任务。替补批次固定为 1，不受普通最小批量放大；仍遵守监控有效期、上一批完成后的刷新、冷却、预算、并发、时段和人工停止。原风控任务交由这个单独机制管理，不额外消耗普通连续失败阈值；其他失败仍按原配置熔断。替补账号若再次明确支付风控，事务内关闭自动补货并递增配置版本，未启动的旧预留不能继续派发；原账号、替补账号、订单均保留，监控与已经提交的付款核实继续。处理后由管理员显式重新启用。

替补关联与暂停结果保存在 `pro_restock_payment_risk`，重启、重复采样、同时预留不会增加替补次数。当前手动／定时全自动流程若因支付风控进入待核实，且保有当前监控池绑定，也进入同一机制；历史普通失败不会在升级时批量领号。

供应商未返回结算结果、处理中、成功状态冲突、缺订单 ID 或明确禁止重试，仍保持原保护。已有成功和结果未知的付款不会因此重做。手动和定时开通的账号核实状态不变。

供应商“结算完成”只说明该服务订单已结算，不代表银行卡已付款或已退款。本次上游只返回“OpenAI 支付风控拦截”，未披露风控规则或具体命中项；不得据此断言 IP、卡或账号资料是原因。
